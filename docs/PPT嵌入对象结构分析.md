# PCFFGRA4 图形二进制中颜色字段的定位方案

- 版本：v1
- 日期：2026-11-13
- 依据：`Fig2.pptx` 实测结果（12 个 Prism 10 对象，单个 `data.bin` 43,674 字节）
- 状态：设计稿，未执行

---

## 一、目标与边界

### 1.1 目标

在 `graphs/{UUID}/data.bin` 这个二进制文件里，找到存储"颜色"的字节位置，并确认其编码方式（RGB 三字节、COLORREF、浮点归一化值，或其他）。定位成功后，"批量替换配色"才具备技术前提。

### 1.2 明确的非目标

- 不追求完整解析 `PCFFGRA4` 格式。只要能稳定读写颜色字段，其余字段（线型、字体、刻度）不碰。
- 不做全格式逆向。逐字段还原 43 KB 结构的工作量远超收益。

### 1.3 前置事实（已实测，不是推断）

| 编号 | 事实 |
|---|---|
| F1 | Prism 10 嵌入对象的数据本体是 ZIP：`CONTENTS` 流前 4 字节为长度，其后为 `PK\x03\x04` |
| F2 | 每个对象含 1 个 `graphs/{UUID}/data.bin`，Fig2 中为 43,674 字节 |
| F3 | 该文件头部 8 字节为 `PCFFGRA4`，无公开格式文档 |
| F4 | 全文只有 19 个可读字符串，按 `color`/`rgb`/`fill`/`pen`/`line`/`palette` 匹配均为 0 条 |
| F5 | 已确认的明文内容仅为轴标题（如 `XTitle-` 后接 `Relative mRNA fold change`） |
| F6 | 安装目录 `PrismXMLSchema.xml` 的描述为 "data and info tables from Prism 9.0"，不含图形设置 |
| F7 | 文件头部存在可辨识的数值序列（`90 01` = 400 出现两次，疑为画布宽高），说明**未压缩**，颜色应是裸值 |

F7 是关键：如果 `data.bin` 被压缩或加密，下面所有方法的成功率都接近零。目前看它是结构化的未压缩数据，所以值得一试。

## 二、四条路线与取舍

| 路线 | 需要你配合 | 工作量 | 成功率估计 | 采用 |
|---|---|---|---|---|
| A 对象间横向比对 | 无 | 小 | 低至中 | 先跑，成本几乎为零 |
| B 已知色值反查 | 无 | 小 | 中 | 先跑 |
| C 极端值对照实验 | 需操作 Prism 两次 | 中 | 高 | 主力方法 |
| D 完整格式逆向 | 无 | 很大 | 高 | 不做 |

路线 A 和 B 可以在你完全不参与的情况下先做一遍，跑完再决定是否动用 C。三条路线共用同一套"编码假设矩阵"，所以先把它定下来。

## 三、编码假设矩阵

给定目标颜色 (R, G, B)，在 `data.bin` 里按以下编码逐一搜索。这是路线 B、C 共用的核心。

| 编号 | 编码方式 | 字节序列示例（纯红 255,0,0） | 依据 |
|---|---|---|---|
| E1 | RGB 顺序，3 字节 | `FF 00 00` | 常见于自定义二进制 |
| E2 | BGR 顺序（Windows COLORREF），3 字节 | `00 00 FF` | Win32 GDI 惯例 |
| E3 | COLORREF 补零，4 字节 | `00 00 FF 00` | GDI 结构体对齐 |
| E4 | RGBA，4 字节 | `FF 00 00 FF` | 若含透明度 |
| E5 | ARGB，4 字节 | `FF FF 00 00` | 若为 uint32 打包 |
| E6 | float32 归一化，3×4 字节 | `00 00 80 3F` ×1 + `00×8` | 0.0–1.0 浮点表示 |
| E7 | float64 归一化，3×8 字节 | 8 字节双精度 | 同上，精度更高 |
| E8 | uint16 扩展，3×2 字节 | `FF FF 00 00 00 00` | 16 位色深 |
| E9 | 65535 归一化浮点 | 与 E6 同构 | 少见 |

**搜索策略**：不逐个盲搜，而是先用"极端色"把候选范围压到最小。纯红 `FF 00 00` 在 E1 下是一串极具辨识度的字节，在 43 KB 里命中次数不会太多；纯蓝 `00 00 FF` 同理。

## 四、路线 A：12 个对象横向比对（零配合）

### 4.1 原理

`Fig2.pptx` 里有 12 个独立 Prism 对象，结构应当同源。如果它们的配色不完全相同，那么逐字节对比就能把"随颜色变化的字节"和"固定不变的字节"分开，颜色字段自然暴露。

### 4.2 做法

1. 从 12 个 `oleObject*.bin` 里各取出 `CONTENTS` 内的 `graphs/*/data.bin`。
2. 按字节位置做多序列比对，统计每个位置在 12 份样本中的取值分布。
3. 输出三类位置：全部相同、部分不同、全部不同。
4. 对"部分不同"的位置，检查相邻 3 至 4 字节是否构成一组、其取值能否映射到某个合理的颜色。

### 4.3 预期与限制

如果这 12 个 panel 用的是同一套配色（很可能，因为同属一张图的多个子图），那么颜色相关字节会落在"全部相同"里，本路线只能定位到标题之类随内容变化的字段，对颜色无效。

**所以这条路线的作用是排除法**：如果 12 份样本的差异位置里出现了 3 字节一组的、取值落在 0–255 的数对，那就有戏；否则直接转 B。

## 五、路线 B：已知色值反查（零配合）

### 5.1 原理

如果图里用过某个具体颜色，而我们知道它的精确 RGB，就可以按 §3 的编码矩阵直接搜。

### 5.2 色值从哪来

两个来源，都不需要你操作：

1. **从 `OlePres000` 的 EMF 里提取**。EMF 是矢量记录流，`EMR_CREATEPEN`(38)、`EMR_CREATEBRUSHINDIRECT`(39)、`EMR_SETTEXTCOLOR`(24)、`EMR_SETBKCOLOR`(25) 等记录内嵌 COLORREF，可以完整还原这张图实际使用了哪些颜色。
2. **从 `ppt/media/*.emf` 里提取**。PPT 为每个对象存了一份预览图，同样是 EMF。

EMF 解析只需按记录头（4 字节类型 + 4 字节长度）顺序遍历，记录类型和字段偏移在 Windows 的 EMF 规范里有定义，是公开标准，不是逆向。

### 5.3 做法

1. 解析 EMF，得到该图使用的颜色集合（去重后通常只有 5 至 15 种）。
2. 剔除黑白灰（这些在二进制里太常见，命中无意义）。
3. 对每种剩余颜色，按 §3 矩阵在 `data.bin` 里搜索。
4. 若某颜色在 E1 或 E2 编码下命中，且命中位置前后结构有规律（例如多个颜色值以固定间隔重复出现），基本可判定找到颜色表。

### 5.4 为什么优先做这条

它是唯一一条能**完全自动化、且不需要你碰 Prism**的路线。如果命中，后面的工作量骤降。

## 六、路线 C：极端值对照实验（需要你配合）

### 6.1 设计思路

如果 A、B 都没命中，说明颜色不是以可识别的方式存的，或者被某种派生量替代（如索引）。此时需要人为制造一个**已知且极端的颜色**，让它在二进制里显眼。

选极端值而不是"好看的颜色"，理由：纯红在 RGB 编码下是 `FF 00 00`，在 BGR 下是 `00 00 FF`，在浮点下是 `00 00 80 3F` 后接八个零——无论哪种编码，都是一串极不自然的字节，比 `2E 5A 88` 这种混合值好找得多。

### 6.2 你需要做的操作（两轮，每轮约两分钟）

**第 1 轮：改成纯红**

1. 打开 `Fig2.pptx`，选一个子图，双击进入 Prism。
2. 只改一处：把某一个数据集的颜色改成纯红 `#FF0000`。路径是 Format Graph → 选中该 dataset → 颜色下拉 → More Colors → 输入 R=255 G=0 B=0。
3. 不要动其他任何设置（不改线宽、不改字体、不改标题）。
4. 关闭编辑窗口，PPT 会问是否更新，选"是"。
5. 另存 PPT 为 `diff_red.pptx`，放在同一个目录下。

**第 2 轮：改成纯蓝**

重复上述步骤，但这次把颜色改成纯蓝 `#0000FF`，另存为 `diff_blue.pptx`。

### 6.3 我这边做什么

1. 提取三份 PPT 里同一个对象的 `data.bin`：原始、红色版、蓝色版。
2. 三份做逐字节比对，只保留"三个样本在这一位置取值互不相同"的位置。
3. 在这些位置中，检验是否符合 §3 的任一编码：红色版应对应 `FF 00 00` 一族，蓝色版应对应 `00 00 FF` 一族。
4. 若同时满足，则字段位置与编码方式同时确定。
5. 反向验证：把原始文件的该位置手工改成红色编码，交给 Prism 打开，看颜色是否真的变红。

第 5 步是关键的确认环节。只有 Prism 认了这个改动，才算真正定位成功，而不是碰巧匹配到别的字段。

### 6.4 为什么两轮而不是一轮

一轮只能找出"与原文件不同的字节"，但这些字节可能是时间戳、修改计数器、缓存校验。两轮取交集，可以排除所有"只随保存动作变化、不随颜色变化"的字节。

如果两轮仍有多个候选位置，再加第三轮（纯绿 `#00FF00`），三色联合可以把候选项压到唯一。

## 七、验证方案

定位到候选位置后，按以下顺序验证，任一步失败即回退。

| 步骤 | 操作 | 通过标准 |
|---|---|---|
| V1 | 在副本上把颜色字节改成另一个值 | 字节写入成功，文件大小不变 |
| V2 | 用 Prism 打开该副本 | 无报错、无"文件损坏"提示 |
| V3 | 查看该数据集颜色 | 显示为新写入的颜色 |
| V4 | 不改动直接另存 | 重新读出的字节与写入值一致（说明无校验和自动修正） |
| V5 | 在 PPT 里双击对象查看 | 颜色更新，且关闭后 PPT 显示同步 |

V4 尤其重要：如果 Prism 保存时会重算某个校验值，那么直接改字节会被判为损坏。这一条能提前暴露该风险。

## 八、若定位成功，能力边界是什么

必须提前说清楚，避免期望落空。

### 8.1 能做的

1. **批量替换 `.prism` 项目文件的配色**：改完直接打开即是新颜色，无额外步骤。这是最干净的场景。
2. **批量替换 PPT 里嵌入对象的配色**：改完 `data.bin` 后需重新打包进 CFBF，再压回 pptx。

### 8.2 不能直接做的

**PPT 里的显示不会自动跟着变。** PPT 显示的是 `OlePres000` 流里的 EMF 呈现缓存，它与 `data.bin` 是两份独立数据。改了后者，前者仍是旧的。

要让显示更新，只有两条路：

- **逐个双击打开再关闭**：Prism 在关闭时会重建缓存。12 个对象就是 12 次双击，比手工改颜色省事，但没到"一键完成"。
- **同时改写 EMF 缓存**：技术上可行（EMF 是公开格式，颜色记录可改），但需要把 EMF 里的颜色按同样的映射替换，再原样写回 `OlePres` 流。这是额外一层工作量，且风险高于改 `data.bin`。

### 8.3 因此的优先级判断

如果目标是"把历史 PPT 里的旧图统一换成新配色"，这条路走通后仍然需要逐一双击刷新，收益打折。

如果目标是"以后所有新图都用统一配色"，那么更有效的做法可能不是逆向二进制，而是在 Prism 里建好 Color Scheme 模板，从源头控制。

**这两件事不冲突**：逆向解决存量，Color Scheme 解决增量。

---

## 九、若全部失败的退路

按顺序回退，不会归零。

1. **只读能力仍然成立**：即使改不了颜色，已经能完整提取原始数据（CSV）、分析参数与结果（JSON）、图表元信息。这本身可以做一个"从 PPT 批量回收数据"的工具。
2. **回到对话框接管方案**：即最初设计的取色面板。它不依赖任何文件格式，改的是输入方式而不是数据，技术风险最低。
3. **Color Scheme 半自动方案**：在 Prism 里预设几套方案，逐图应用。纯手工，但零风险。

## 十、执行顺序与所需配合

| 阶段 | 内容 | 需要你做什么 |
|---|---|---|
| P1 | 路线 A：12 个对象横向比对 | 无 |
| P2 | 路线 B：从 EMF 提取色值并反查 | 无 |
| P3 | 依据 P1、P2 结果决定是否进入 C | 你判断 |
| P4 | 路线 C：极端值对照实验 | 操作 Prism 两轮，各约两分钟 |
| P5 | 验证 V1 至 V5 | 配合打开文件查看 |

P1 与 P2 可以合并成一次运行，输出一份报告。若 P2 命中，P4 可以跳过。

---

## 十一、需要你确认的事

1. **是否接受 P1、P2 先跑**。这两步全自动、只读，不改 `Fig2.pptx`，产物写在 `输出/` 下。
2. **是否愿意做 P4 的两轮操作**。这是成功率最高的一步，但需要你动手。
3. **优先级判断**：你要解决的是"存量 PPT 里的旧图"还是"以后新图的配色统一"？前者值得逆向，后者用 Color Scheme 更省事。这个答案会改变后续投入方向。
